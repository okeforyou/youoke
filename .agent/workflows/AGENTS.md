# 🛡️ YouOke: AGENTS.md - กฎการรบ (Rule of Engagement)

นี่คือ "คัมภีร์หลัก" ที่ Agent (AI) ทุกตัวต้องอ่านและปฏิบัติตามอย่างเคร่งครัดในโปรเจกต์ YouOke เพื่อรักษาคุณภาพและความเสถียรของระบบ

### 1. 📋 ขั้นตอนการทำงาน (Strict Workflow)
ก่อนแก้ไขโค้ดใดๆ Agent **ต้อง** รายงานในรูปแบบภาษาไทย 5 หัวข้อนี้:
1.  **เป้าหมาย (Goal)**: จะทำอะไรในงานนี้
2.  **สิ่งที่ต้องแก้ (To-be-Changed)**: รายชื่อไฟล์และบรรทัดที่จะแก้ไข (ระบุให้เจาะจงที่สุด)
3.  **ผลกระทบ (Impact)**: จะมีผลอย่างไรต่อฟีเจอร์อื่นๆ และยืนยันว่า "ระบบเดิมต้องไม่พัง"
4.  **แนวทางแก้ไข (Resolution)**: อธิบายวิธีการทางเทคนิคแบบคร่าวๆ
5.  **ความเข้ากันได้ของดีไซน์ (Design Harmony)**: การันตีว่า UI ที่เพิ่มใหม่ต้องกลืนไปกับ Design Token เดิม (Vanilla CSS / Master Pattern)

### 2. 🚫 กฎเหล็ก (Non-Negotiables - ห้ามละเมิดเด็ดขาด)
- **ห้าม "Nuclear Revert"**: ห้ามใช้คำสั่งย้อนกลับไฟล์ทั้งโปรเจกต์ หรือย้อนกลับทั้งโฟลเดอร์โดยปราศจากการตรวจสอบผลกระทบต่อฟีเจอร์อื่น (กฎ Chromecast Rule)
- **ห้าม "Drive-by Refactor"**: ห้ามแก้โค้ดส่วนที่ไม่เกี่ยวข้อง, ห้ามจัดฟอร์แมตไฟล์ใหม่หากไม่ได้รับอนุญาต และห้ามแอบ "Optimize" โค้ดที่ทำงานได้ดีอยู่แล้ว
- **Surgical Edit เท่านั้น**: ทุกการแก้ไขต้องกระทำแบบ "ผ่าตัดเฉพาะจุด" คือแก้ให้น้อยที่สุดเพื่อผลลัพธ์ที่ตรงจุดที่สุด (Strict Minimalist)
- **Logic Integrity (ห้ามสลับฝั่ง)**: หากงานเป็นเรื่องดีไซน์ (UI/CSS/Tailwind) **ห้ามแตะต้องบรรทัด Logic (onClick, addDoc, fetch, database write)** โดยพลการเด็ดขาด และห้ามตัดสินใจเปลี่ยนวิธีเขียนจาก Client-side (Browser) ไปเป็น Server-side (API) เองโดยไม่ได้รับการยืนยันว่าสิทธิ์การเข้าถึง (Admin SDK/FCM) ในเครื่องผู้ใช้พร้อมทำงาน

### 3. 🚦 ระบบการอนุมัติ (Approval System)
1.  **เสนอแผน (Proposal)**: Agent อธิบายแผนตามข้อ 1 และหยุดรอ
2.  **รออนุมัติ (Wait for GO)**: ห้ามลงมือจริงหรือใช้เครื่องมือแก้ไขใดๆ ในเทิร์นแรกที่เสนอแผน
3.  **ลงมือ (Execute)**: เมื่อได้รับอนุญาต (เช่น คำว่า "ลุย" หรือ "ไป") จึงจะเริ่มแก้ไขไฟล์ได้
4.  **รายงานหลังจบ (Final Check)**: ทุกครั้งที่ Push ต้องตรวจสอบว่าไม่ได้แอบลบ Import หรือทำไฟล์อื่นหายไป

### 4. 📐 YouOke Master Dashboard Standards v1.0 (Mobile-First)
มาตรฐานงานดีไซน์ Dashboard และ Admin UI ทั้งหมดต้องยึดถือรูปแบบดังนี้:
- **Base Layout**: พื้นหลังระดับหน้าจอใช้สีเทาอ่อน (`bg-slate-50`), ระดับ Card ใช้สีขาวบริสุทธิ์ (`bg-white`)
- **Container Pattern**: ขอบมนคงที่ `rounded-xl` (12px), ขอบเส้นบาง `border-slate-100`, เงาบางเบา `shadow-sm`
- **Spacing Guidelines**: ระยะห่างมาตรฐานคือ `p-4` (Mobile) และ `p-6` (Desktop), ช่องว่างระหว่างก้อนข้อมูล `gap-4`
- **Information Hierarchy**:
    - **Label**: ขนาด 11px, ตัวหนามาก (`font-bold`), สีเทาเรียบ (`text-slate-400`), ตัวพิมพ์ใหญ่ (**UPPERCASE**) วางไว้เหนือข้อมูล (Top-Label)
    - **Value/Input**: ฟอนต์สีเข้ม (`text-slate-900`), ขนาดมาตรฐาน 14-16px, เน้นการอ่านง่าย
- **Touch-Friendly Layout**: ปุ่มและ Input ต้องมีระดับความสูงอย่างน้อย 44px (Standard Touch Target)
- **Minimalist Aesthetic**: ห้ามใช้ Gradients ฉูดฉาด, ห้ามใช้ Pulse Animations ที่ไม่จำเป็น, ห้ามใส่เงาหนา (Solid & Flat Design เท่านั้น)

### 💡 การเรียนรู้และไอเดีย (Ideas & Innovations)
- หาก Agent มีไอเดียเจ๋งๆ หรือวิธีที่ฉลาดกว่าเดิม **ต้องเสนอในหัวข้อ "ไอเดียเสริม"** ในขั้นตอนเสนอแผนก่อนเสมอ ห้ามแอบใส่มาในโค้ดหากยังไม่ได้รับความเห็นชอบ

### 👤 ตัวตน (Identity)
- **สไตล์การสื่อสาร**: มืออาชีพ เป็นทางการแบบทีมพัฒนาคุยกัน (Dev-to-Dev), กระชับ, เน้นเป้าหมายทางเทคนิค และสื่อสารเป็นภาษาไทย
- **เป้าหมาย**: ผลิตผลงานที่มีคุณภาพสูง มีมาตรฐานเดียวกัน (Consistency) และรองรับการนำไปใช้ต่อในอนาคต ระบุ version ที่แก้ไขทุกครั้งที่ footer พร้อม changlog(Scalability)
